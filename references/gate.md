# 该不该动手：客户端可改，还是服务端权威

`re gate` 是这条判定树的自动化版本。文件名/字符串只是线索，**结论必须能落到调用点或接口响应上**；
这一页记录的是判定顺序、每条信号的含义，以及实战里踩过的坑。

## 1. 先问一个问题

> "用户看到的那个结果（能不能看 / 能不能用 / 是不是会员），是谁算出来的？"

三种答案，对应三种做法：

| 答案 | 判据 | 做法 |
|---|---|---|
| 客户端自己算 | 逻辑随包下发：Flutter 的 `libapp.so`（Dart AOT）、RN 的 `index.android.bundle`、Unity 的 `assets/bin/Data`、PE 里的本地标志位 | 改判定点（`re patch`），改完必须验证行为 |
| 服务端算，客户端只展示 | 接口返回加密信封；权益字段/播放地址/订单状态由响应决定；本地只有 `isVip` 之类的镜像字段 | 改客户端只能改"显示"，改不了"结果"；要找服务端那条链路 |
| 混合 | 服务端下发配置，客户端按配置渲染（付费墙模型、广告位） | 先看配置里哪个字段是"开关"，再决定改解析还是改渲染 |

## 2. 判定顺序（`re gate` 的权重就是这个顺序）

1. **加固？** 命中 `PACKERS` 里的壳库 → +3。有壳先脱壳（`re unpack` / 内存 dump），别在壳上打补丁。
2. **本地完整性校验？** `getPackageInfo`、`signatures`、`getApkContentsSigners`、
   `nativeVerifyIntegrity`、`ensureVerified`、`isTampered` → +2。
   有它就意味着"改包会被自己发现"，先找过签点，否则改什么都会触发自检失败。
3. **权益/付费墙模型？** `paywall`、`isVip`、`vipLevel`、`is_vip`、`DramaPaywall`、`entitlement` → +1。
   只是说"客户端里提到了会员"，不说明谁能决定。
4. **支付/订单？** `alipay`、`wechatpay`、`/order`、`/pay`、`/vip/` → +2。订单落库的在服务端。
5. **框架可改性？** Flutter / RN / Unity → -2。逻辑随包，客户端有落点。
6. **接口形态（`--probe`）**：加密信封（`"hash": true`、长 base64、签名头）→ +3；
   明文 JSON 且带 `items`/`data` 列表 → -2；401/403 → +2。

合计 ≥ +3 判"疑似服务端权威"，≤ -2 判"客户端可改"，中间是"证据不足"。
**"证据不足"不是"不能改"，是"还没找到决定性证据"**。

## 3. 实战对照（这三例都是真的）

| 目标 | 信号 | 结论 | 后来验证 |
|---|---|---|---|
| 串口调试助手（Delphi PE） | 注册函数只读 `GetLocaleInfoA` 的语言 ID，返回"已注册/未注册" | 客户端可改（本地标志） | 改判定 → 直接"已注册" |
| VOFA+（Qt PE） | 有硬编码 RSA 公钥 + `RSA_public_decrypt`（+3），也有 `registered` 本地标志（-3） | **验签结果最后落在本地标志上 → 客户端可改** | 把两个判定函数改成恒真 → 面板变"已授权" |
| 黄果短剧（Flutter APK） | 有壳（+3）、有 `nativeVerifyIntegrity`（+2）、付费墙模型 `fromJson`（+1）、支付串（+2） | 服务端权威 | 改 `isVip`/`isConfigured` 后界面无变化；判 `isConfigured=false` 反而触发"线路检测失败"自检 |

结论模式：**"有验签"不等于"只能服务端说"，关键看验签结果落在哪**——
落在本地标志位，改标志；落在服务端下发的播放地址/订单状态，改客户端没用。

## 4. 反面清单（今晚踩过的坑，别再犯）

- **别先动"全局开关"**：把广告 SDK 的 `isConfigured` 判死会连带触发 App 自己的启动自检
  （表现为"线路检测失败"这种与网络无关的报错）。要改就改"渲染点"，不要改"配置态"。
- **别只改一个 getter 就宣布解锁**：`isAWVIP`/`isRechargeVIP` 改真之后界面一模一样，因为
  付费墙是服务端下发的图片/文案 + 服务端签名的播放地址。改前先 `re gate`。
- **别忽略打包器**：带壳的 APK 改完包要先过完整性校验（`nativeVerifyIntegrity` 这类），
  否则连启动都过不去；过签和改逻辑是两件事。
- **别在真样本上直接改**：先复制一份，`--dry-run` 演算，改完 `re dis` 复核、`re pe` 确认节表，
  再拿去跑。
- **别把静态字符串当结论**：`signatures` 可能只是权限声明，`subscribe` 可能只是 UI 文案。
  信号只用来决定"下一步查哪里"。

## 5. 下一步怎么选

- 判"客户端可改" → 找判定点的调用链（`re xref` → `re decompile --at`）→ `re patch` 改 → 跑行为验证。
- 判"疑似服务端权威" → 先 `--probe` 确认接口形态；再看同一份内容有没有**另一条接口**
  （镜像站、公开 API、旧版客户端协议）。有的话，改客户端不如换数据源。
- 判"证据不足" → 补三样东西：抓包（请求/响应）、运行时日志、调用栈。
  三样都拿不到，就不要承诺"能改"。

## 6. 第四档：「换数据源」什么时候比改客户端划算

判定树原本只有三档，实战里还有第四种结局：**内容本身在另一条接口上是免费/公开的**，
这时改客户端是下策。满足下面三条再考虑换源：

1. 同一份内容能从另一条接口拿到，而且**不需要登录态**（今晚的镜像站 `/api/videos` 就是）；
2. 关键字段完整：列表、详情、**播放地址**（签名 m3u8 + 分片都取得到），不是只有元数据；
3. 那条接口有**稳定的发布渠道**（官方发布页/镜像清单），不是一次性域名。

换源失败的退路：镜像全挂时回到"服务端权威"这一档，别硬改客户端。

## 7. 「证据不足」补到什么程度算够

按顺序补，满足任一条就升级判定：

- **接口证据**：对业务接口（详情/播放/权益）各 probe 一次，看响应体里有没有 `hash:true`、
  长 base64、`items`/`data` 列表、401/403。只看首页 403 不算证据——那是网关，不是业务。
- **调用点证据**：`re xref`/`re decompile` 找到付费墙模型（`DramaPaywall` 之类）的解析点，
  看字段是不是服务端下发；找到 `nativeVerifyIntegrity` 的调用点，看它在不在启动/请求链路上。
- **运行证据**：抓包（请求头/响应体）+ 运行时日志 + 崩溃栈，三样至少两样。

三样都拿不到，就停在"证据不足"，不要承诺"能改"——今晚在 `isConfigured` 上就是先动手后翻车。
